# PRD 작성 메타 프롬프트

> 이 문서는 Claude Code에 그대로 붙여넣어 `docs/PRD.md`를 생성하기 위한 **메타 프롬프트**입니다.
> 아래 `---` 구분선 이후의 내용을 프롬프트로 사용하세요.

---

## 역할 (Role)

당신은 10년 차 시니어 프로덕트 매니저(PM)이자 테크니컬 라이터입니다.
스타트업 MVP 범위를 명확히 자르고, 개발자가 바로 구현에 착수할 수 있는 수준의 PRD를 작성하는 데 능숙합니다.

## 목표 (Goal)

**"노션(Notion)에 입력한 견적서 내용을 클라이언트가 웹에서 확인하고 PDF로 다운로드할 수 있는 서비스"** 의 **MVP PRD 문서**를 작성하고, `docs/PRD.md` 파일로 저장하세요.

## 사전 조사 (반드시 먼저 수행)

PRD를 쓰기 전에 아래 자료를 읽고 제약 조건을 파악하세요.

1. `CLAUDE.md` — 기술 스택, 명령어, 작업 완료 체크리스트
2. `docs/guides/project-structure.md` — 폴더 구조 규칙
3. `docs/guides/nextjs-15.md` — Next.js 15.5.3 패턴 (App Router, Server Components, Server Actions)
4. `docs/guides/component-patterns.md`, `docs/guides/styling-guide.md` — UI 컴포넌트/스타일 규칙
5. `docs/guides/forms-react-hook-form.md` — 폼 처리 규칙
6. `package.json`, `src/` 현재 구조 — 이미 설치된 의존성과 기존 코드

외부 라이브러리(Notion API, PDF 생성 등)의 최신 사용법이 필요하면 **context7 MCP**로 공식 문서를 확인한 뒤 반영하세요. 기억에만 의존하지 마세요.

## 확정된 제품 맥락 (변경 금지)

| 항목 | 내용 |
| --- | --- |
| 데이터 소스 | Notion 데이터베이스 (견적서 원본, 관리자가 Notion에서 직접 입력) |
| 사용자 | ① 관리자(견적서 작성자, Notion 사용) ② 클라이언트(견적서 열람자, 로그인 없음) |
| 핵심 가치 | 관리자는 Notion만 쓰면 되고, 클라이언트는 링크 하나로 견적서를 보고 PDF를 받는다 |
| 기술 스택 | Next.js 15.5.3 (App Router + Turbopack), React 19, TypeScript 5, TailwindCSS v4, shadcn/ui (new-york), Zod |
| 제약 | 별도 DB 없이 Notion을 단일 데이터 소스로 사용 (MVP) |

## MVP 범위 가이드

### 반드시 포함 (Must)

- Notion API 연동으로 견적서 데이터 조회 (서버 사이드, API 키는 환경 변수로만 관리)
- 견적서 상세 웹 페이지 (고유 URL로 접근, 반응형)
- 견적서 PDF 다운로드
- 견적서 존재하지 않음/조회 실패 등 오류 상태 화면
- 다크/라이트 테마 대응 (기존 스타터 템플릿 기능 활용)

### 검토 후 판단 (Should) — 포함/제외 여부와 근거를 PRD에 명시

- 견적서 목록 페이지 (관리자용)
- 링크 접근 보호 (만료일, 비공개 토큰 URL 등)
- 인쇄 최적화 스타일
- 캐싱/재검증 전략 (ISR, `revalidate`)

### MVP에서 제외 (Won't) — "향후 확장"으로 분리

- 클라이언트 로그인/회원가입
- 견적서 수락/서명/결제 기능
- 이메일 발송
- 자체 견적서 작성/편집 UI
- 다국어 지원

## 작성해야 할 PRD 구성

`docs/PRD.md`는 아래 섹션을 **순서대로** 포함하세요.

1. **개요**
   - 프로젝트명, 한 줄 요약, 배경과 해결하려는 문제
2. **목표와 성공 지표**
   - 목표 3개 이내, 측정 가능한 성공 기준 (예: 링크 접속 후 PDF 다운로드까지 3클릭 이내)
3. **사용자 및 페르소나**
   - 관리자 / 클라이언트 각각의 상황, 니즈, 페인포인트
4. **사용자 여정 (User Flow)**
   - 관리자: Notion 입력 → 링크 공유
   - 클라이언트: 링크 접속 → 견적서 확인 → PDF 다운로드
   - Mermaid 다이어그램으로 표현
5. **기능 요구사항**
   - 표 형식: `ID | 기능명 | 설명 | 우선순위(Must/Should) | 인수 조건`
   - 기능 ID는 `FR-001` 형식, 인수 조건은 검증 가능한 문장으로 작성
6. **Notion 데이터 모델**
   - 필요한 데이터베이스 속성 정의 표 (속성명 | Notion 타입 | 필수 여부 | 설명)
   - 견적서 항목(품목, 수량, 단가, 금액), 클라이언트 정보, 발행일/유효기간, 비고 등
   - 합계/세금 계산 규칙 (Notion Rollup/Formula로 처리할지, 앱에서 계산할지 결정하고 근거 기재)
   - Zod 스키마 초안 (TypeScript 코드 블록)
7. **화면 설계**
   - 페이지 목록과 라우트 (`app/` 기준), 각 화면의 구성 요소와 상태(로딩/빈 상태/오류)
   - ASCII 와이어프레임 최소 1개 (견적서 상세 화면)
   - 재사용할 shadcn/ui 컴포넌트 목록
8. **기술 설계**
   - 아키텍처 개요 (Server Components 중심, 데이터 흐름 다이어그램)
   - Notion API 연동 방식과 환경 변수 목록 (`.env.example` 포함)
   - PDF 생성 방식 비교(예: `@react-pdf/renderer` vs Puppeteer vs 브라우저 인쇄)와 **MVP 권장안 및 선정 근거**, 서버리스 배포 환경 제약 포함
   - 캐싱/재검증 전략
   - 예상 폴더 구조 (`docs/guides/project-structure.md` 규칙 준수)
9. **비기능 요구사항**
   - 성능(LCP 등 목표치), 보안(API 키 노출 금지, 접근 제어), 접근성, 브라우저 지원, 한국어 PDF 폰트 처리
10. **리스크 및 가정**
    - Notion API 레이트 리밋, PDF 한글 폰트, 링크 유출 등 리스크와 대응 방안
    - 확정되지 않은 가정은 별도 표시
11. **개발 단계 (마일스톤)**
    - Phase 단위로 분할하고 각 Phase의 산출물과 완료 조건 명시 (이후 `docs/ROADMAP.md`의 입력으로 사용됨)
12. **향후 확장 로드맵**
    - MVP 제외 항목을 우선순위와 함께 정리
13. **미결정 사항 (Open Questions)**
    - 사용자 확인이 필요한 질문 목록

## 작성 원칙

- **언어**: 한국어로 작성합니다. 기술 용어와 코드 식별자는 원문을 유지합니다.
- **MVP 집중**: 범위를 넓히지 말고, 모호하면 "제외"를 기본값으로 하되 근거를 적습니다.
- **검증 가능성**: 모든 기능 요구사항에는 테스트 가능한 인수 조건을 붙입니다.
- **일관성**: 용어(견적서, 클라이언트, 관리자 등)를 문서 전체에서 통일합니다.
- **스택 정합성**: `CLAUDE.md`에 명시된 스택과 충돌하는 기술을 제안하지 않습니다. 새 의존성이 필요하면 이유를 명시합니다.
- **추측 금지**: 확인되지 않은 사실(API 제한, 라이브러리 기능 등)은 단정하지 말고 context7로 확인하거나 "가정"으로 표시합니다.
- **분량**: 개발자가 20~30분 안에 읽을 수 있는 분량으로, 표·목록·다이어그램을 적극 활용합니다.

## 진행 방식

1. 먼저 위 **사전 조사**를 수행하고, 발견한 제약 사항을 5줄 이내로 요약해 보고합니다.
2. 사용자 결정이 꼭 필요한 항목(예: 링크 보호 방식, PDF 생성 방식)이 있으면 한 번에 모아 질문합니다. 합리적 기본값이 있으면 질문하지 않고 기본값으로 진행하고 PRD의 "가정"에 기록합니다.
3. `docs/PRD.md`를 작성합니다.
4. 작성 후 아래 **자체 검수 체크리스트**로 점검하고 결과를 보고합니다.

## 자체 검수 체크리스트

- [ ] 13개 섹션이 모두 존재하는가
- [ ] 모든 Must 기능에 `FR-ID`와 인수 조건이 있는가
- [ ] Notion 데이터 모델과 화면 설계가 서로 일치하는가
- [ ] MVP 제외 항목이 기능 요구사항에 섞여 있지 않은가
- [ ] 환경 변수·보안 요구사항에 API 키 노출 방지가 포함되어 있는가
- [ ] 한국어 PDF 폰트 처리 방안이 명시되어 있는가
- [ ] 마일스톤이 `docs/ROADMAP.md` 작성의 입력으로 쓸 수 있을 만큼 구체적인가
- [ ] 미결정 사항이 별도 섹션으로 정리되어 있는가

## 최종 출력

- 채팅 응답: 핵심 결정 사항 요약(5줄 이내), 미결정 사항 목록, 다음 단계 제안(`docs/ROADMAP.md` 작성)
- **커밋은 하지 않습니다.** 사용자가 검토·승인한 뒤에 진행합니다.
